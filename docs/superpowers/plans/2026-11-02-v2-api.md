# V2 API: many shops per owner and per barber. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** an owner may have many shops and a user may barber in many shops (one profile per shop), with every barber or owner operation naming the profile or shop it acts on, and no person booked in two places at once.

**Spec:** `docs/superpowers/specs/2026-11-02-v2-many-shops-design.md`

## Global Constraints

- Same layering as v1: domain and application never import adapters; ESLint enforces it.
- Error codes: someone else's shop → `NOT_SHOP_OWNER`; someone else's or a removed profile → `NOT_A_BARBER`; `ALREADY_A_BARBER` means "already in this shop"; `SHOP_ALREADY_OWNED` is gone.
- The cross-shop overlap maps to `SLOT_UNAVAILABLE`, like the per-barber one.

## Review Focus

- Two bookings for the same person at two shops at the same moment: exactly one succeeds, under concurrency.
- A reschedule or `rescheduleSlots` at shop A must not offer times taken at shop B.
- Every mutation that takes an id rejects an id that belongs to someone else, without revealing whether it exists.
- Existing rows survive the migration: appointments get `barber_user_id` from their barber.
- Accepting an invite to a shop where the user already barbers fails cleanly, also under a concurrent `becomeBarber`.

### Task 1: Data model

- Migration `1793560000000-many-shops.ts`: drop `barbershops_owner_id_key`, add `barbershops_owner_idx`; replace `barbers_active_user_idx` with `barbers_active_user_shop_idx (user_id, shop_id) WHERE removed_at IS NULL`; add `appointments.barber_user_id uuid NOT NULL REFERENCES users(id)` filled from `barbers.user_id`, the exclusion constraint `appointments_barber_user_no_overlap` (booked only) (its gist index also serves the person's busy-time query, so no separate `(barber_user_id, starts_at)` index was added).
- `Appointment` gains `barberUserId`; `AppointmentRepository.busyFor(barberUserId, ...)` reads by person; the new constraint maps to `SLOT_UNAVAILABLE`.
- [ ] Tests: unit, `availableSlots` at shop B leaves out José's booking at shop A; integration, two parallel bookings for José at A and B at the same time → one `SLOT_UNAVAILABLE`; migration test sees the new index and constraint. Commit.

### Task 2: Shops for many

- Repositories: `BarbershopRepository.listByOwner`, `BarberRepository.listActiveByUser` and `findActiveInShop(userId, shopId)` replace `findByOwner` and `findActiveByUser`.
- Guards: `requireOwnedShop(deps, actorId, shopId)`, `requireOwnBarber(deps, actorId, barberId)`, `assertNotBarberingIn(deps, userId, shopId)`.
- Use cases take the id: `updateBarbershop(shopId)`, `inviteBarber(shopId)`, `becomeBarber(shopId)`, `listInvites(shopId)`, `updateBarberProfile(barberId)`, `createService(barberId)`; `removeBarber`, `revokeInvite`, `updateService` and `archiveService` check ownership through the entity.
- [ ] Tests: an owner creates two shops; a barber accepts invites to two shops and gets two profiles; a second invite to the same shop gives `ALREADY_A_BARBER`; another owner's shop id gives `NOT_SHOP_OWNER`; another user's barber id gives `NOT_A_BARBER`; services are per profile. Commit.

### Task 3: Scheduling by profile

- `ownBarber(deps, userId, barberId)` replaces `barberOfUser`; `setWeeklySchedule`, `blockDate`, `unblockDate`, `mySchedule`, `barberAgenda` take `barberId`. `ShopDirectory.barberOfUser` goes away.
- [ ] Tests: hours and days off are per profile; another user's profile id gives `NOT_A_BARBER`. Commit.

- SDL and resolvers as in the spec's table, including `agendaChanged(barberId)`; descriptions list the new errors.
